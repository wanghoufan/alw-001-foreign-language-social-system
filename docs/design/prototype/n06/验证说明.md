- 校验脚本：`docs/design/prototype/n06/verify.mjs`
- 结果文件：同目录 `verify-result.json`（每次运行覆盖）
- 最近一次运行：2026-11-09（47 节日接入 + 人物/作品/聊天 P0 修复后重跑），`RESULT PASS · 80/80 checks · 22 screenshots`
- 运行环境：macOS 26.6、Node v24.19.0、Google Chrome 156.0.8078.81（无头 `--headless=new`，独立临时 profile）

## 一、怎么运行

```bash
cd docs/design/prototype/n06
node verify.mjs
```

- 不需要本地服务、不需要 `npm install`、不联网。
- 脚本把页面当作 `file://` 直接打开；截图写入 `screenshots/`，结论写入 `verify-result.json`。
- 退出码：`0` 全通过；`1` 有断言失败；`2` 脚本自身异常。日志逐条打印 `PASS/FAIL/SHOT`。
- 只跑一次即可，不要循环重试：失败信息里已带实测值，按值定位。

## 二、脚本做了什么

1. 启动无头 Chrome，`--user-data-dir` 指向 `os.tmpdir()` 下的临时目录，结束即删除；不占用用户 Chrome 的 profile，不打开可见窗口。
2. 用 CDP 打开 `file://.../n06/index.html`，固定 393×852、DPR 2、移动端模拟。
3. 按路由驱动交互（点击筛选、切 Tab、打开全屏、导入、切主题），每步用 `Runtime.evaluate` 读真实 DOM / 计算样式 / 命中测试。
4. 采集 `Runtime.exceptionThrown`、`Log.entryAdded`、`Network.loadingFailed`，把 JS 异常与资源失败计入断言。
5. 截图与像素统计同批产出，保证截图和断言描述的是同一状态。

## 四、本轮新增的关键断言

原脚本只判断 `img.naturalWidth > 0`，这条在“照片已加载但被提示盖住”时依然为真，等于测不到问题。现在改为四层：

1. **状态层**：每个 slide 的 `.fallback` 必须 `hidden === true` 且计算样式 `display === 'none'`。
2. **可见层**：每个 `img` 的 `display !== none`、`visibility !== hidden`、`opacity === 1`。
3. **层叠层**：`document.elementFromPoint(slide 中心)` 必须命中 `IMG`；另有一条全页面扫描，任何可见 `.fallback` 只要与某张可见图片区域重叠且自己命中在最上层，就判失败。
4. **像素层**：把 `#gallery .slide` 区域截图后在页面内用 canvas 解码，统计亮度标准差、量化颜色数、“缺图板底色 `#f6f9f6`”占比。

### 像素证据的判据

| 指标 | 阈值 | 本次实测 | 含义 |
|---|---|---|---|
| 亮度标准差 sd | ≥ 18 | 82 | 纯色板接近 0；照片纹理明显 |
| 量化颜色数 | ≥ 200 | 2215 | 纯色板只有 1–2 种 |
| 缺图板底色占比 | ≤ 0.6 | 0.000 | 超过一半是 `#f6f9f6` 即说明被面板盖住 |

阈值取自“注回旧写法”的实测分布（sd 28、颜色 101、底色占比 0.947）与正常照片（sd 82、颜色 2215、底色 0）之间的明显间隔，没有为了通过而放宽。

## 六、`file://` 独立打开与图片路径

- 页面无 `fetch`/`XHR`、无外链，数据全部由 `assets/repo-data.js`、`assets/data.js` 内联提供，因此双击 `index.html` 即可运行。
- 图片根路径：`assets/app.js:14` 的 `IMG_ROOT = '../../../成果整理/Hainan-Travel-Guide/images/'`，相对 `index.html` 解析到 `docs/成果整理/Hainan-Travel-Guide/images/`；文件名 `encodeURI` 处理中文目录。
- 断言 8 会把 `img.currentSrc` 转成文件系统路径逐个 `fs.existsSync`，确认不是“浏览器缓存里看着有、磁盘上其实没有”。
- 兼容性注意：脚本启动参数带 `--allow-file-access-from-files`，那是为测试稳定性加的更宽松开关；页面本身只需要同目录子资源，属于普通 `file://` 能力。

## 七、已知限制

1. 只覆盖 Chrome 无头渲染。Android WebView（正式验收机 OPPO PLG110 / ColorOS）未测，WebView 对 `file://` 子资源的限制也未验证。
2. 只测 393 宽度的截图；375/430/520 只跑横向溢出，没有逐张出图。
3. 浏览器 `speechSynthesis` 只用于演示，不等于豆包 / 云端 TTS 验收。
4. 触摸手势未用真实手指测试，翻页通过按钮与 `scrollLeft` 驱动。
5. 图片目录被 `.gitignore:56` 排除：换机、干净克隆或素材目录缺失时，原型没有照片，脚本会如实转红（缺图提示出现），这不是原型逻辑错误，但需要在交付说明里讲清。
6. 本轮未做 OPPO 真机、未打包、未跑正式 APP 的全量回归。

## 八、结论

`verify-result.json` 的 80 项全部通过；关键断言具备“可红”能力的证据来自旧 37 项套件的反向自检（已红 5 项），当前 79 项套件未重跑反向自检。这只能证明**原型在 Chrome 下的交互与出图正确**，不等同于正式 APP 已修复、也不等同于真机验收通过。
