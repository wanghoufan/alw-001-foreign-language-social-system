### G1 · 导航形态：顶栏 tabs 被整体推翻为左侧边栏

1. **原来怎么说**：原方案 §10 只列了 5 个入口的名字（Today/People/Topics/Practice/Review）与各自内容，**没有任何一句话描述它们放在屏幕的哪里**（早期方案文档:450-494）。
2. **后来实际怎样**：`151aa27`（10-05）实现为 `<header>` 内的横向 tabs（`git show 151aa27:public/index.html` 第 7 行 `<header>…<nav class="tabs" id="tabs">`）；`262ac05`（10-11 14:30）整体改为 `<div class="shell"><aside class="sidebar">…<nav class="tabs">`，并给每项补了字符图标（`index.html:12,15,75`）。
3. **差在哪里**：差的不是功能，是**信息架构的容器**。顶栏 tabs 在 5 项以内尚可，但本项目的 5 项里有 2 项（Topics、People）自带「列表 + 阅读」双栏结构，屏幕横向空间被顶栏吃掉后双栏更挤（`styles.css:179` 的 `290px + 1fr` 就是证据）。这是做了才知道的。
4. **为何本应提前思考**：导航形态是「页面骨架」，骨架一改，header/footer/主题切换器/搜索框的位置全部要跟着改。本次 `262ac05` 一次性改了 `index.html` 10 行、`styles.css` 110 行，正是因为它们是耦合的。
5. **不提前会造成何种返工**：一次骨架级重构（HTML 结构 + 110 行 CSS + 主题切换器从顶栏搬到侧栏底部）；若当时已有截图基线，还要重截 3 张图。
6. **下次普通人怎么说**：「我要左边一条竖着的菜单，右边显示内容，点菜单不要整个页面刷新；不要上面一排横着的按钮。」
7. **提前明确的收益**：省掉 1 次骨架重构（约 120 行改动）+ 主题切换器的二次摆放 + 截图的重做。

**责任区**：**计划者应主动发现**。用户不可能知道「顶栏 vs 侧栏」是个需要回答的问题；计划者看到「5 个入口 + 其中 2 个是列表—阅读结构」，应当主动提出形态二选一并让用户拍板。开发者无责（按默认实现了最省事的顶栏）。

## §5 按类别的根因追溯

### 5.1 UI / 布局 / 导航 / 页面密度

**根因：原方案把「视觉完整度」整体推迟到 Human Gate 之后（早期方案文档:769「在 Human Gate 前，以功能闭环可验证为目标，不追求视觉完整度」），但没有给视觉项另开一个「Day1 是非题清单」。**

后果链：需求侧空白 → 开发者按默认做顶栏 tabs 与无主题 → 用户看到后给参考截图（HANDOFF.md:9）→ 一次性爆发 515 行 → 紧接着 3 分钟内改控件、50 分钟后删「跟随系统」、58 分钟后改布局。

**可复用经验**：UI 里只有两类东西可以推迟——**颜色微调**（主观，必须看了才知道）和**文案润色**；**骨架类（导航位置）、结构类（主题有几套）、控件形态类（下拉/分段/弹层）、默认态类（打开是哪套）必须在 Day1 问完。** 这四类一旦返工，改动量都是 40 行以上且会连带 CSS 与截图。

页面密度方面，本项目做对了一件事：首页用 4 张编号流程卡把主链路画出来（`index.html:89`），这属于「高频操作前置」；做慢了一件事：话题页的双栏 + 搜索 + 记住上次阅读（`index.html:93,127-140`）是 `b8b78df` 才补的，说明「列表 + 阅读」这类高密度页面的交互细节原方案完全没定义。

### 5.2 操作体验

`b8b78df` 一次补齐了 toast、一键复制（带 `execCommand` 回退）、空态文案、防重复提交、必填校验、记住上次阅读（`index.html:35-43,91,127-140,159-180`）。这些都是**可用性的地板**，不是锦上添花。

**根因**：原方案通篇在讲数据规范与隐私红线，操作体验只在 §16 的验收标准里以「30 秒内记录一个人」「1 分钟内整理一次聊天」这类**时间指标**出现（早期方案文档:705-706）。时间指标是对的，但它没有对应的交互手段——要做到 30 秒，就必须有 toast、有必填校验、有记住上次位置。

**下次做法**：把时间指标翻译成交互清单。「30 秒记录一个人」= 表单字段 ≤ 5 + 必填校验 + 回车提交 + 创建后 toast + 就地刷新列表（本项目 `index.html:91,173,177-178,181` 恰好就是这套）。

### 5.3 外部依赖与部署

三层外部条件，全部是 Day1 未预见、事后才处理的：

1. **端口 4173 冲突**：Docker 常驻容器占用 4173，本地调试必须 `PORT=4174`，且「不得擅自停 Docker 容器」（HANDOFF.md:41；README.md:34）。
2. **ChatGPT Live 的能力边界**：不能写本机文件、倾向给摘要 → 逼出 G6 的整条产物规范。
3. **三份数据**：项目内 `SocialMate-Data/`（本地运行读）vs `~/DockerData/alw-001-foreign-language-social-system/`（容器读，本次取证 mtime 停在 2026-10-05 11:10~11:11）vs `~/DockerBackups/.../predeploy-20261006`（仅 10-06 一次快照）。**仓库内没有任何同步记录**，本地新增的人物/互动是否进了容器，无法从仓库判断。

**根因**：部署被当作「功能做完后加一层」，而不是「一开始就决定数据只有一份在哪」。

### 5.4 质量验证

- 做对的：Test A–G 覆盖了建人物、加互动、沟通卡、话题包、练习提示词、重启持久化、预览—确认—拒绝陈旧—路径越界，本次 `node --test test/acceptance.test.mjs` 实测 7/7 通过（Node v24.19.0）。安全面也测到了：`test:82` 断言 `../README.md` 返回 400。
- 做错的：① 无 UI 自动化，界面正确性只有一句人工记录；② `test:51-54` 用「前端 HTML 字符串包含」来断言 UI，导致**改一个中文文案就会让测试红**——测试与文案强耦合，是脆弱测试；③ 验收命令没固化，README.md:60 的写法带目录参数会失败；④ `CHANGELOG.md` 断更，`f2e4dbc`/`00aec27`/`262ac05` 三次「为什么改」零记录。

**根因**：原方案 §13 把「测试闭环」写得很细（Test A–G 逐项期望），但没有配套要求「这些测试必须是可一键执行的命令」和「UI 也要有回归手段」。

## §10 终审摘要（B 路）

本项目的需求文档写得极好，好到几乎可以直接当验收单用——781 行里把数据真源、目录结构、人物档案字段、AI 复盘十项输出、沟通卡格式、话题包十四项要素、五个入口、Test A–G、安全红线十条、禁止事项十一条、Human Gate 七问全部写清楚了。这也是为什么 `151aa27` 一次提交就能交付后端 + 前端 + 初始化 + 7 个验收用例（+1102 行）而没有出现功能级返工。真正的问题只有一个源头：**这份文档把「外观与导航」整体留白，并且用「不要过度设计 UI」「Human Gate 前不追求视觉完整度」两句话给它盖了个合法的章**。

后果在 2026-10-11 集中爆发：`b8b78df`（13:32）一口气 +515 行做三主题与一堆交互优化；3 分钟后 `f2e4dbc` 把切换器从下拉菜单改成分段按钮；50 分钟后 `00aec27` 删掉「跟随系统」并把默认改成晨光；58 分钟后 `262ac05` 把顶栏 tabs 整体换成左侧边栏。四次提交，三次是推翻刚做完的东西，而这三个答案——主题几套、切换器长什么样、导航放左边还是上边——全都是用户第一次开口就能回答的。更刺眼的是 `docs/handoff/HANDOFF.md` 写于 14:14，8 分钟后就被 `00aec27` 推翻，16 分钟后被 `262ac05` 再次推翻，而这份交接文档至今未提交（`git status --porcelain` = `?? docs/`），意味着仓库里连一份「当时认可的是什么」都留不下来。

第二个根因是「真源可以不止一个」这件事没有被当成纪律。数据规范 `00-README.md` 同时存在于 `scripts/initialize-data.mjs:6` 的模板和被手改的磁盘文件里，前者没有「口语练习学习材料」那一章，后者有；因为初始化用 `flag:'wx'` 永不覆盖（`initialize-data.mjs:23`），这个差异会永久保留，并在换机器重新初始化时静默降级。同一类问题出现在部署侧：代码副本与 HEAD 逐字节一致（实测 diff 0 行，这点做对了），但数据副本 `~/DockerData/alw-001-foreign-language-social-system/` 的 mtime 停在 2026-10-05 11:10~11:11，与项目内数据目录不构成可验证的同一份。再加前端提示词里硬编码的 `/Users/zzymima0000/Developer/coding/1.Active/alw-001-外语社交系统`（`index.html:104-105`），结论是：**这个项目目前只在这台机器的这个路径下成立**。

第三个根因是质量验证的两头不均衡。后端很强：`test/acceptance.test.mjs` 的 7 个用例本次实测 7/7 通过，连「预览后文件被并发修改 → apply 返回 409」「`../README.md` → 400」这类边界都测到了。前端为零：没有 UI 自动化，界面正确性只靠 HANDOFF.md:15 一句人工记录；而 `test:51-54` 用「HTML 字符串包含」来断言前端，导致改一句中文文案就会让测试变红——这是脆弱测试，不是真回归。验收命令也没固化：README.md:60 写 `node --test`，实测带目录参数会报 `MODULE_NOT_FOUND`。

给终审的三条可复用结论：**一，UI 里只有颜色和文案允许事后微调，骨架/结构/控件形态/默认态必须在 Day1 问完**；**二，任何规范文件必须只有一个真源，脚本生成的就不要手改**；**三，交接文档如果不入库，就等于没有交接**——本项目的 HANDOFF 恰恰在写完 8 分钟后被推翻且从未入库。
