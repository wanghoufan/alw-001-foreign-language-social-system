## §1 与 A 路的争议裁定（五行式）

### D1 · 「数据目录放项目内，是为了 Docker 挂载便利」这个推断成立吗

- **主张 A（V1.0 §4.4）**：「推断（无证据）：为了省一次路径配置、并让 Docker 的 `APP_DATA_DIR` 挂载更容易对齐」。
- **主张 B（V1.0 G5）**：判为「开发者+计划者责任」，并推断「放项目内 + gitignore 最省事」。
- **原始证据**：`.env.example:8` `APP_DATA_DIR=/absolute/path/to/DockerData/alw-001-foreign-language-social-system`；`README.md:41`「真实 Markdown 数据挂载自 `~/DockerData/alw-001-foreign-language-social-system/`」；`~/DockerData/alw-001-foreign-language-social-system/00-README.md` mtime 2026-10-05 11:11。也就是说：**Docker 化之后，数据最终还是被搬到了项目外的 `~/DockerData/`**，「放项目内」并没有带来挂载便利，反而多了一次搬移。
- **判定**：**A 的推断证据不足，予以删除**。真正可证实的只有「原始要求（分离）与实现（项目内）相反，且无解释记录」。至于动机，三种可能（图省事 / 用户后来改主意 / 为初始化脚本省一次路径配置）都无法排除，**维持「归属未证实」**。B 自己的「图省事」推断同样降格为推断，不再作为结论。
- **仍不确定**：谁在什么时候做的这个决定——**未证实**。

### D2 · 「用户机器的绝对路径」该不该列为 A 类（开工硬阻塞）

- **主张 A（V1.0 §8 A4）**：把「用户机器的绝对路径（会被写进提示词）」列为 **A 类硬阻塞**，理由是「目前硬编码在前端提示词里」。
- **主张 B（V1.0）**：未单列此项。
- **原始证据**：`public/index.html:104-105` 硬编码 `/Users/zzymima0000/Developer/coding/1.Active/alw-001-外语社交系统`；而 `server.mjs:46` 的 `/api/health` **已经返回 `dataDir` 字段**（`send(res,200,{ok:true,host:HOST,dataDir:DATA_DIR})`）。
- **判定**：**应降级为 B 类（开发者自办）**。理由：路径不需要用户「提供」，服务自己就知道；开发者应当在渲染提示词时从 `/api/health` 取 `dataDir` 注入，而不是问用户要。**把它列为 A 类会让「问用户」变成掩盖实现缺陷的借口。** A 的 §6「V1 必须有」第 14 条（A V1.1 §4）已经把它改成「不写死 / 运行时注入」，与本判定一致。
- **仍不确定**：注入后提示词是否还需要在别处出现项目根路径——`index.html:106` 还引用了 `SocialMate-Data/00-README.md` 的相对路径，可由 `dataDir` 推导，**无阻塞**。

## §2 B 自身遗漏补充（V1.0 未覆盖）

### 2.1 部署副本同步范围不完整（新增 G13）

HANDOFF.md:39 的纪律是「`cp public/*` 过去再 `docker compose … up -d --build`」，实测结果是 `public/` 与 `server.mjs` 同步到位，但 `README.md` 停留在 2026-10-06 版（3249 字节）。**后果**：部署副本里的操作说明是过期的（不含 10-11 补的功能介绍、三主题、wiki 布局与练习记录规范）。不影响运行，但任何人照部署副本的 README 操作会读到旧信息。

### 2.2 双语 README 的持续维护成本（新增 G14）

`ce2b104`（10-05）引入 `README.en.md`（107 行）后，`bef53d0`、`a9cc032` 每次都要改 2 个文件。两份 README 里都写了三条绝对路径（`~/Developer/coding/docker/…`、`~/DockerData/…`、`~/DockerBackups/…`，`README.md:41`、`README.en.md:58-61`）。**任何路径变更要改四处**（中、英、部署副本、实际目录）。

### 2.3 错误处理可诊断性（新增 G15）

`server.mjs:113` 的 catch-all 把「文件不存在 / JSON 解析失败 / 路径越界 / 请求体过大」一律映射为 400。而同一文件在 `/api/apply` 里明确区分了 400（确认参数不完整）与两种 409（内容不一致、主档已变化），在 `/api/people` 里也用了 409「同名人物已存在」（`server.mjs:67`）。**说明作者有能力区分，只是兜底处没做。**

### 2.4 跨设备数据通道与一条安全红线（新增 G16）

`学习资料/00-说明.md`（工作树，被 gitignore）规划了 `01-口语自测原始记录/` 与 `02-学习分析/{周度回顾,月度回顾,专题分析,阶段总结}/`，但**这些子目录均不存在**（`find 学习资料 -type f` 仅返回 `.DS_Store` 与 `00-说明.md`）。文档末段写：

> 「手机 Android 应用要直接写入此路径，必须存在可用的共享挂载、同步提供方或受控传输桥接；仅把这条 Mac 路径填进 Android 代码并不能使它可访问。配置桥接前，应先确认现有运行环境和授权，不要擅自开放公网或局域网服务。」

这条红线被正确守住了（`server.mjs:10` 绑 `127.0.0.1`；compose 只发布 `127.0.0.1:4173`；README.md:37「不支持手机局域网访问」）。**这是使用时才浮现的第二类外部依赖**，Day1 完全未预见，且自带授权与安全约束。

### 2.5 提交说明体为空的量化

12 次提交中**只有 `b8b78df` 有说明体**（3 条），其余 11 次说明体为空（已用 `git log --format=%b` 复核）。而恰恰是 `f2e4dbc`（改切换控件）、`00aec27`（删跟随系统）、`262ac05`（改布局）这三次**最需要说明「为什么」的提交，说明体全部为空**。这不是巧合：它们都是「用户看了一眼就要求改」的产物，改动发生在对话里而不是文档里。
