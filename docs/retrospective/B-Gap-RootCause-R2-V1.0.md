## 3. 本轮新增差距证据链（七问逐项）

### G1｜视觉/版式判据：先做紧凑，再全局放大，再修布局

1. **原来怎么说**：上一轮只沉淀「主题四问」，字号/密度从未进入需求问题清单；用户全局规则后立「正文 ≥19px、控件 ≥15px、标题 ≥23px」。
2. **后来实际怎样**：V1.6 底部导航字号 11.5px（`CHANGELOG.md:53` 整改记录）；0.9.9 才补字号线（正文 19/标题 23/控件 15/最小 14，`HANDOFF.md:36`）；字放大后卡片撑到 463px、人物字母头像占位，又修回 296px/76px（`agent.md:60`）；OPPO 底部出现 46px 双份安全区留白（`agent.md:54`）。
3. **差在哪里**：没有人先问「用户手指多大、眼神如何、手机多大」，字号是被屏幕逼出来的，不是需求给的。
4. **为何本应提前思考**：这是随身手机 App，用户在海南户外边走边看，19px 级别的大字是该场景第一不变量；且用户全局规则早已存在，开工时把规则映射成 CSS 变量只要一次。
5. **不提前造成何种返工**：至少三轮字号/布局返工（11.5→15px 整改、0.9.9 字号线、0.9.12 卡片/头像/留白修复），每轮都是「改一处样式→真机才能发现→再改」。
6. **下次普通人怎么说**：「我要在手机上看清字，别让我戴老花镜；按钮要一指头按得中。」
7. **提前明确的收益**：一条 CSS 令牌基线 + 一次 393px 视口走查即可锁定，三轮返工变一轮。

### G2｜系统深色模式：旧问题换载体复发

1. **原来怎么说**：上一轮裁定「主题四项是非题（几套/默认/控件形态/跟随系统）Day1 问完」（Lessons ③1）。
2. **后来实际怎样**：Android WebView 继承系统深色后「白字白底不可读」，11-01 被迫强制浅色（提交 d121804 标题，间接）；0.9.2 才补真正的深色适配 `#192d35`（`CHANGELOG.md:31`）。
3. **差在哪里**：第一轮问清了「要不要跟随系统」这个 Web 层问题，没人问「手机系统切到深色时 App 跟不跟」——WebView 场景下系统主题会渗透进来。
4. **为何本应提前思考**：目标是 Android WebView，系统主题渗透是平台默认行为，属「地板级」问题，与第一轮主题四问同构。
5. **不提前造成何种返工**：一次不可用级故障（白字白底）+ 一次方向反转（强制浅色 → 重做深色）。
6. **下次普通人怎么说**：「我晚上手机调深色，你的 App 别变成白花花一片刺眼。」
7. **提前明确的收益**：在 WebView 加 `prefers-color-scheme` 断言一行 CSS，可省一次故障修复与一次返工。

### G3｜朗读引擎选型：四次换道 + 机型适配踩空

1. **原来怎么说**：第一轮无 TTS 需求；V1.1 起原生系统 TTS（`docs/architecture-facts.md:30` provider 默认 `system`）。
2. **后来实际怎样**：系统 TTS → Mac 中继 → 豆包 Web Audio（11-05）→ 原生豆包直连（11-08）；音色 `Ruth` 报 55000000 需白名单（`agent.md:37`）；`<audio>` 连播被 autoplay 拦截改 Web Audio（`docs/risks.md:203`）；OPPO 无系统 TTS 引擎致学习页无声（`docs/qa/2026-11-08-oppo-record-audio/README.md:28`），再改「有豆包 Key 默认 remote」（`agent.md:58`）；线程池 release 后复用崩溃（`agent.md:59`）。
3. **差在哪里**：每一步都由当下故障驱动，从未有一次「目标机型清单 + 各机型 TTS 能力探测」的前置动作。
4. **为何本应提前思考**：TTS 是核心练习功能，而 Android 生态的 TTS 引擎碎片化是已知事实；用户 11-08 换 OPPO 是可预期事件（换机本来就计划内）。
5. **不提前造成何种返工**：播放架构两次重写（`<audio>`→Web Audio→原生队列直连），三次真机级故障（第二句变系统声、OPPO 无声、线程池崩溃）。
6. **下次普通人怎么说**：「我新手机上没有那种念文章的声音，你能不能用豆包的声音，别让我听不了。」
7. **提前明确的收益**：Day1 定「云端合成为主、系统 TTS 仅回退」，省两次架构改写。

### G4｜换机迁移：默认值按第一台手机写死

1. **原来怎么说**：无（换机场景 Day1 不存在）。
2. **后来实际怎样**：OPPO PLG110 首次录音报「未配对或令牌失效」——新机 `asr_mode` 默认 `mac`（`agent.md:57`）；原生朗读 `provider` 默认 `system` 而新机 prefs 为空（`agent.md:58`）；需迁移 people 8/cards 1/media 3 等（`HANDOFF.md:36`）。
3. **差在哪里**：默认值隐含假设「已配对的旧机」，没有按「全新安装冷启动」场景定义默认态。
4. **为何本应提前思考**：换机/重装是移动 App 的必经场景，且本项目有真实 Key 与本地库，迁移成本高。
5. **不提前造成何种返工**：两次「新机必踩」默认值修复 + 一次迁移脚本补写（0.9.12 才稳定）。
6. **下次普通人怎么说**：「我换新手机，装上就要能用，别让我猜哪个开关。」
7. **提前明确的收益**：首次启动引导页（模式选择+Key 录入+迁移导入）一次性消除整类问题。

### G5｜双份页面：三年前的坑用新方式复发

1. **原来怎么说**：上一轮 G8「规范双真源」、④7「源/产物双份改了不生效」已入踩坑，且 11-04 已沉淀 skill `dual-copy-page-sync-local-zh`（`RETRO-20261104.md:84`）。
2. **后来实际怎样**：11-08 仍有「重跑 `build-v12.py` 会覆盖 V1.5–V1.7 手改；页面真源是 `socialmate-v1.2/index.html`，勿重跑旧脚本」（`agent.md:56`）；11-08 同日「补丁被插进已有 style 块内部成无效 CSS，grep 命中不等于生效」（`agent.md:53`）。
3. **差在哪里**：skill 沉淀了但脚本的「唯一真源」没有机械化——构建脚本仍指向旧基线，靠人记「别跑它」。
4. **为何本应提前思考**：上一轮已把「双真源」定为流程失误最高优先级之一，复发说明沉淀只到了文档层，没到工具层。
5. **不提前造成何种返工**：改完前端真机不生效的排查每轮 10–20 分钟（`agent.md:13,19,55` 三条同类），以及一次潜在的手改被覆盖。
6. **下次普通人怎么说**：「我改的东西怎么手机上看不到？你改之前先告诉我改哪个文件才算数。」

### G6｜交付与仓库脱节：真机版本领先 git 五天

## 6. 根因追溯（四类，追到底）

### 6.1 UI/交互
- **现象**：字号、深色、吸顶、留白、卡片截断反复修（`agent.md:53-60`）。
- **根因**：视觉需求从未被转成数值判据，验收矩阵里没有「最小机型视口 × 深/浅色 × 系统字号放大」的组合；每次都是真机实拍才暴露。用户全局规则「先把形容词转成判据」正是对此的事后立法。

### 6.2 操作体验
- **现象**：换机必踩默认值（G4）；`openReviewPage` 返回 true 但界面未切（`STATUS-20261107.md:56`）；桌面端必然失败的「开始录音」（`PRODUCT_BACKLOG.md:57-60`）。
- **根因**：接口语义与场景默认值没有契约——「受理≠完成」「新装≠已配对」「桌面≠手机」三种区分都靠故障倒逼。缺一条设计约束：「任何返回值与默认值必须回答『在全新环境第一次使用时它是什么』」。

### 6.3 外部依赖
- **现象**：OPPO 无 TTS、MIUI 安装拦/安全键盘、无 SIM 误判 4G 失败（`agent.md:35`）、DeepSeek 503（`risks.md:144`）、豆包鉴权方式与文档不符（`risks.md:207`）。
- **根因**：把「设备/厂商/云商」当同质环境。缺一张开工前「环境探针清单」（TTS 引擎有无、SIM 状态、默认输入法、安装权限、鉴权方式实测一条），全局规则「能力探测先于选型」是事后立法。

### 6.4 质量验证
- **现象**：报告先写 PASS 后修正、fixture 混入生产、回环当真人、`S.session` 污染测试数据（`agent.md:44`）。
- **根因**：**报告生成者与证据核验者是同一主体**。NOT_RUN/PARTIAL 纪律与预算闸已建立（这是本轮最大进步），但「复核须由独立主体重跑」仍缺位——V1.6 首轮不实是被分角色审查抓出来的，不是自查抓出来的。
