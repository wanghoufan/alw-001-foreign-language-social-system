## ① 最初目标、已核实状态、历史覆盖度与证据缺口

### 1.1 最初目标（原始需求原文）

用户在海口，希望把「认识外国朋友 → 外语练习 → 翻译辅助 → AI 社交复盘」整合成一个**长期可积累的本地系统**（早期方案文档:13）。核心闭环（:17）：

> 线下认识人 → 记录基本资料与沟通内容 → AI 自动复盘并结构化 → 下次见面前生成沟通卡 → GPT Live 做口语模拟 → 真人交流 → 再次复盘 → 持续更新人物档案。

第一阶段六原则（:23-30）：本地数据为 SSOT；Markdown 优先；UI 只是入口、AI 只是加工层；先验证每天真的有用再谈原生 App；不提前建登录/云同步/复杂数据库/多端账号；只记对方主动分享或用户亲自确认的事实，禁止 AI 推断隐私/心理/关系状态。

## ⑥ UI / 布局 / 导航 / 页面密度 / 高频操作的可复用经验

### 6.1 可以推迟的只有两类
**颜色微调**与**文案润色**。其余四类——骨架（导航位置）、结构（主题几套）、控件形态（下拉/分段/弹层）、默认态（打开是哪套）——必须在 Day1 问完。这四类任一返工，改动量都在 40 行以上，且会连带 CSS 与截图基线。

### 6.2 页面密度
- **做对的**：首页用 4 张编号流程卡（01 准备话题 / 02 练习 / 03 整理 / 04 看档案）把主链路画出来，每步一个按钮直达（`index.html:89`）——这是「高频操作前置」的标准做法。

- **做慢的**：以上两套高密度交互都是 `b8b78df` 才补的，原方案完全没定义——说明「列表+阅读」型页面的交互细节必须在需求阶段就写。

## ⑨ 适用范围、反例与不可通用化的部分

### 9.1 适用范围
- Local-first、单人使用、数据为文件（Markdown/YAML）、无账号无云端的**个人知识管理类**项目。
- 由 AI 辅助、但**AI 不内嵌**（以提示词外挂）的项目。
- 有 Docker 常驻部署习惯的个人开发环境。
- 项目规模对标：12 次提交、约 1900 行自有代码（server 119 + index 228 + styles 287 + init 27 + test 83 + 模板数据）。

### 9.2 反例（本方法论在这些情况下不适用或要改写）
1. **多人协作 / 有真实用户量的产品**：本项目的「11/12 提交说明体为空」在单人项目里只是可追溯性损失，在团队项目里会直接导致协作失败；「需求文档出版本库」在团队里是致命的。
2. **需要 Web 可访问的产品**：本项目的「只绑 127.0.0.1」「不支持局域网」是隐私优先的选择，不能照搬到需要多人访问的系统。
3. **有视觉设计师参与的项目**：「主题四项是非题必须在 Day1 问完」在有设计师时会由设计阶段承担，不需要用户回答。
4. **数据敏感但要求自动化的项目**：本项目刻意不接 AI API、靠人工搬运产物；若要求自动化，⑥.6 的「预览—确认」与「人工搬运」两条都要重新设计。
5. **前端复杂到需要框架的项目**：本项目的「单文件 HTML + 内联 JS」在 228 行时可读，超过一定规模后「无 UI 测试」的代价会急剧放大。

### 9.3 不可通用化的部分（明确标注）
- 「Node 零依赖、无 package.json」是本项目能成立的前提之一，**不是普适最佳实践**；它同时导致了 UI 测试缺位。
- 「三套主题的具体命名（晨光/墨夜/松林）」「5 档难度」「海口/海南场景」是本项目特有内容，不可复用。
- 「数据规范双真源」这一条虽然是本项目的问题，但**「脚本生成 + 永不覆盖（`flag:'wx'`）」本身是对的**（保护手改内容），问题出在改规范时漏改生成器——不要因噎废食改成「脚本每次覆盖」。
- 「部署副本 `cp public/*`」是本用户的目录约定，换环境要重定。

### 10.2 具体下次做法（可执行，不是口号）

**用户侧**
- 第一次开口时，把 §8-A 的 9 条是非题照着回答一遍；不确定就说「你给我推荐一个默认，我后面再改」。
- 明确说出「哪些视觉项允许事后微调」，避免陷入无止境配色反馈。
- 要求「需求文档与交接文档都留在版本库里」。

**计划者侧**
- 收到需求后，先做一次「留白扫描」：**凡是需求里没写但 UI 必然要有的维度（导航位置、主题套数与默认、高频控件形态、空态、错误反馈），全部挑出来做成人话选择题**。本项目 781 行里「主题/配色/深色/外观/浅色」零命中，就是扫描没做。
- 把原方案的「时间指标」（30 秒记录一个人）翻译成交互清单（字段 ≤5 + 必填校验 + 回车提交 + toast + 就地刷新）。
- 验收必须写成「一条命令 + 一份打勾清单 + 3 张截图」，写进需求的验收章节，而不是做完才补。
- 建立「原始要求 → 实现」对照追踪：原方案明写「数据目录与代码目录分离」，实现若相反必须留一条决策记录。

**开发者侧**
- 规范文件单一真源：改规范时同步改生成器（本项目 `994fa56` 改了 README/模板/前端/测试，独漏 `initialize-data.mjs:6`）。
- 机器路径运行时注入（`/api/health` 已返回 `dataDir`），不写死。
- 错误分类：至少区分「请求错 400 / 不存在 404 / 被改过 409」，不要 catch-all 400。
- 每次提交写说明体，特别是「推翻刚做的东西」时——本项目 11/12 为空，其中 `f2e4dbc`/`00aec27`/`262ac05` 恰恰是最需要说明的三次。
- CHANGELOG 随功能提交更新（本项目只有 10-06 一条）。
- 部署同步给**文件清单**而不是「`cp public/*`」（README 漏了）。
- **清理前先问**：这份文档是不是唯一的 Day1 证据？是就移进 `docs/`，不要移进 gitignore 目录。
- 交接文档必须入库（HANDOFF.md 至今 `?? docs/`，且写完后 8 分钟即被推翻）。
