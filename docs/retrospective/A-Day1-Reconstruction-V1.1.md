## §2 A 自身遗漏补充（V1.0 未覆盖的证据与结论）

### 2.1 跨设备数据桥接：一个被写进文档、但至今未落地的外部依赖

`学习资料/00-说明.md`（工作树，被 gitignore）规划了两个目录 `01-口语自测原始记录/` 与 `02-学习分析/{周度回顾,月度回顾,专题分析,阶段总结}/`，但**这两个目录实际都不存在**（`find 学习资料 -type f` 只返回 `.DS_Store` 与 `00-说明.md`）。文档里还写了一条关键的外部约束：

> 「这是 Mac 上的项目目录。手机 Android 应用要直接写入此路径，必须存在可用的共享挂载、同步提供方或受控传输桥接；仅把这条 Mac 路径填进 Android 代码并不能使它可访问。配置桥接前，应先确认现有运行环境和授权，不要擅自开放公网或局域网服务。」（`学习资料/00-说明.md` 末段）

**这是 Day1 完全没预见、后来才出现的第二类需求**（第一类是口语练习产物）：真实使用中出现了一款 Android「懒得打字」应用，需要把它的导出物送进 Mac 的项目目录。它牵涉三件事——设备间桥接方案、授权、以及一条**明确的安全红线**（不得为了桥接而开放公网或局域网）。这条红线与 `server.mjs:10` 的 `127.0.0.1`、compose 的 `127.0.0.1:4173` 是一致的，说明它被正确地守住了。

**补进 Day1 清单**：「我的资料会不会有来自手机/其他设备的？如果有，用什么方式进来？不许为了让它进来而把服务开放到公网或局域网。」

### 2.2 双语 README 的持续维护成本

`ce2b104`（10-05）引入 `README.en.md` 后，此后每一次 README 改动都必须同步英文：`bef53d0` 改 2 个文件（+73/-9）、`a9cc032` 改 2 个文件（+10/-14）。英文版共 107 行、中文 66 行，含全部部署路径与健康检查命令。**这是一份需要永远同步两份的文档**，而两份里都写了三条绝对路径。任何路径变更都要改四处（中/英 README + 部署副本 + 实际目录）。

**补进 Day1 清单**：「要不要中英文两份说明？如果要，谁负责同步？」

### 2.3 错误处理的可诊断性缺口（V1.0 完全没提）

`server.mjs:113` 是一个 catch-all：`catch (err) { return send(res, 400, { error: err.message || '请求失败' }); }`。这意味着**读取不存在的文件、JSON 解析失败、路径越界、请求体过大，全部返回 400**。

- 好处：不泄漏内部细节（`test:82` 的越界断言就是 400）。
- 坏处：**错误码语义丢失**，AI 整理助手或用户在排障时无法从状态码区分「文件不存在」与「我的请求写错了」。对比之下，`/api/apply` 的三种失败（确认参数不完整 400 / 内容不一致 409 / 主档已变化 409）与 `/api/people` 的 409「同名人物已存在」（`server.mjs:67`）是区分过的——说明作者**有能力区分，只是在兜底处没做**。

**补进 Day1 清单**：「出错时要告诉我错在哪一类：是我写错了、还是文件不存在、还是被别人改过了。」

## §11 终审素材包（A 路 · V1.1，≥600 字）

**一、这个项目最该被记住的，是「需求写得好」带来的收益有多大。** 781 行原始方案（2026-10-04，现仅存于被 gitignore 的 `temp/`）在数据真源、目录结构、人物档案字段、AI 复盘十项输出、沟通卡格式、话题包十四项要素、五个入口、Test A–G、安全红线十条、禁止事项十一条上写得极其具体。结果是 `151aa27`（2026-10-05）一次提交就交付了后端 + 前端 + 初始化脚本 + 7 个验收用例（+1102 行），并且**没有出现任何功能级返工**。本次复核隐私红线落地情况时，7 条红线全部能在代码或模板里找到对应（`server.mjs:56` 的关系阶段白名单、`server.mjs:80,94` 的双 409、`initialize-data.mjs:9,10` 的来源标注与不得推断声明、`Prompts/聊天复盘.md` 的禁止条款）。这是一条可以直接引用的因果：**需求具体到可执行，实现就不会跑偏；需求留白的地方，就是返工发生的地方。**

**二、而这个项目的留白恰好集中在外观与导航上。** 已用 grep 复核：781 行里「主题/配色/深色/外观/浅色」零命中，只有 3 处出现「UI」，且其中一句是「不要过度设计 UI」（:696），另一句是「Human Gate 前不追求视觉完整度」（:769）。这两句话给外观留白盖了合法的章。代价在 2026-10-11 集中支付：`b8b78df`(13:32) +515 行做三主题与交互优化；3 分钟后 `f2e4dbc` 把切换器从下拉菜单改成分段按钮；50 分钟后 `00aec27` 删掉「跟随系统」并把默认改为晨光；58 分钟后 `262ac05` 把顶栏 tabs 整体换成左侧边栏。四次提交，三次推翻刚做完的东西，而这三个答案全是用户第一次开口就能回答的（用户手上甚至已有参考截图，HANDOFF.md:9）。按 D5 的裁定，可预防的部分是四项是非题——主题几套、默认哪套、控件形态、是否跟随系统；不可预防的只有「色值好不好看」，而这一项至今悬空（HANDOFF.md:27）。

**三、互审给我补上了两个 A 路自己漏掉的维度。** 其一是跨设备数据通道：`学习资料/00-说明.md` 里写着 Android 应用导出物要送进 Mac 项目目录，并明确「必须存在共享挂载或受控传输桥接……不要擅自开放公网或局域网服务」。这是使用时才浮现的第二类需求，且它自带一条安全红线——这条红线被正确守住了（`server.mjs:10` 的 127.0.0.1、compose 只发布 `127.0.0.1:4173`）。其二是错误处理的可诊断性：`server.mjs:113` 的 catch-all 把「文件不存在 / JSON 解析失败 / 路径越界 / 请求体过大」一律映射成 400，而同一份文件在 `/api/apply` 里明明区分了 400 与两种 409——说明作者有能力区分，只是兜底处没做。这两条都不影响「能不能用」，但都影响「用坏了能不能查」。

**四、B 路有一处归因我要明确修正。** B 把「数据目录未与代码分离」判给了开发者与计划者，但仓库内 12 次提交里有 11 次说明体为空（已用 `git log --format=%b` 复核，唯一有说明体的是 `b8b78df`），没有任何一处记录解释这个选择。它可能是图省事，也可能是用户后来改了主意，也可能为了 Docker 挂载对齐——三种都无法排除。我维持「结论受限」，把责任标为**归属未证实**，B 的推断降格为推断。

**五、最后一件事必须写进终审：这个项目的历史被自己削掉了一块。** `5698685`（2026-10-11 14:55）把 781 行需求文档从版本库删除，`b956852` 把它移进被 gitignore 的 `temp/`。同期还在补英文 README 与 Docker 说明，推断是为公开做准备。后果是：任何未来的 clone 者都看不到 Day1 需求，只能看到成品代码与 README；而本文与 B 文对「原来怎么说」的全部引用，都依赖一份不在版本库里的文件。同一类问题还有 `docs/handoff/HANDOFF.md`——它写于 14:14，8 分钟后被 `00aec27` 推翻，16 分钟后被 `262ac05` 再次推翻，而它至今是未提交的工作树文件（`git status --porcelain` = `?? docs/`）。**交接文档不入库，就等于没有交接。**
